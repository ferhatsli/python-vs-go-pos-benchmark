# Benchmark Methodology

This repository models **production-inspired POS backend workloads**. It does not reproduce or disclose a specific production system.

## Track A question

Go was already the leading architectural candidate. Track A was designed to answer a narrower engineering question: how large is the practical performance gap between a frozen Python/FastAPI stack and a correctness-equivalent Go stack under the same benchmark conditions?

Track A is not a theoretical language shootout and it is not a tuned-maximum comparison.

## Controlled variables

The paired benchmark keeps these conditions aligned between runtimes:

- the same PostgreSQL instance and schema/index set;
- the same Redis service where the workload requires it;
- deterministic synthetic D1, D2, and D3 datasets;
- the same load-generator scripts and scenario semantics;
- the same transaction, lock, idempotency, and correctness expectations;
- the same application CPU and memory limits;
- the same application database connection budget;
- only one measured runtime active at a time.

Application limits for Track A:

- Python API: 2 CPU / 1 GiB
- Go API: 2 CPU / 1 GiB
- PostgreSQL: 4 CPU / 4 GiB
- Redis: 0.5 CPU / 256 MiB
- load generator: 2 CPU / 1 GiB
- application DB pool maximum: 40

## Dataset profiles

| Profile | Devices | Stations | Companies | Payment scale |
| --- | ---: | ---: | ---: | ---: |
| D1 | 500 | synthetic | synthetic | baseline |
| D2 | 5,000 | synthetic | synthetic | scaled |
| D3 | 50,000 | 5,000 | 500 | ~1,000,000 |

The dataset sizes are independent from k6 VU or arrival-rate settings.

## Repetition and stability

Each canonical matrix uses:

1. Python warmup ×2;
2. Go warmup ×2;
3. measured P→G, G→P, P→G, G→P, P→G;
4. at least five measured trials per runtime;
5. additional measured trials when p95 coefficient of variation is above 10%;
6. a maximum of ten measured trials;
7. `UNSTABLE` classification if CV remains above 10% at ten measured trials.

Headline normalized values use medians across measured trials. Raw per-run values remain evidence for the stability classification.

## Correctness hard gate

A performance result is invalid if the trial violates financial or lifecycle invariants. The accepted Track A evidence did not permit:

- duplicate payment;
- QR double redemption;
- RF double spend;
- negative wallet or duplicate debit;
- idempotency mismatch;
- illegal command transition;
- partial financial commit;
- incorrect worker alarm behavior.

Performance is reported only alongside correctness status.

## Stop-escalation

At an extreme load level, a scenario stops escalating when the canonical run shows a correctness failure, sustained database-health failure, generator saturation, material host swapping/OOM, or an equivalent capacity failure defined by the benchmark plan. A failed level is itself a result; the benchmark does not tune one runtime mid-matrix and retry the same comparison.

## Historical source freeze vs public reproduction

The original Track A run was established against a frozen private source snapshot. Its historical provenance is retained in `docs/source-freeze/public-provenance.json` without publishing the private repository.

Public users run the self-contained benchmark with `ISOLATION_MODE=public`. That mode verifies the public benchmark checkout and provenance boundary; it intentionally does not claim to revalidate the private historical source tree.

## Evidence hierarchy

The publication distinguishes:

- **canonical paired evidence** — results generated by the frozen AB/BA matrix;
- **canonical capacity failure evidence** — a frozen canonical run that triggered stop-escalation;
- **diagnostic evidence** — additional investigation used to understand a failure, never substituted for a paired canonical result.

If a diagnostic number is not backed by a retained raw artefact in the public evidence package, that number is excluded from public quantitative claims.
